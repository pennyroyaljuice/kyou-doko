# 検索の現行仕様と検証（2026-11-02）

2026-11-03の種類別候補収集・主分類による判定・同程度の候補での分類分散は [THEME_DISCOVERY.md](THEME_DISCOVERY.md) を参照。

## 採用・表示のルール

- 上限は必須。時間は分、距離はkm。往復は往路と復路の実測合計で判定し、上限超過は返さない。
- 下限は任意の目安。空欄と0は同じ扱い。下限以上を優先し、不足した場合は下限未満も補充して最大8件を返す。
- 候補選びは上限への近さを優先し、上限の3%幅で同程度となる候補の間で方向を分散する。方向内の候補列も同じ近さの帯で並べ、高評価だけを先に並べて近さを打ち消さない。
- 高評価・レビュー数では評価あり・口コミ1件以上の場所だけを対象とする。全種類でNearbyのDISTANCEを使い、近さの帯と地理分散を優先した上で、細かな時間・距離差より各指標を先に比較する。詳細は [RATING_SEARCH_SELECTION.md](RATING_SEARCH_SELECTION.md) を参照。
- 一覧の並び替えは取得済み候補の順序だけを変え、候補数を変えたり検索APIを呼んだりしない。
- さらに調べるは前回の範囲・起点を維持し、既出とアカウントの除外IDを経路確認前に除外する。追加結果は重複なくマージする。
- 自転車は徒歩経路の距離を15km/hで換算する推定値。高速道路の指定は車のみ。

## 今回確認した問題と修正

1. 近場でも8件揃うと経路確認を打ち切り、残りの候補を確認していなかった。既存の最大24回という経路予算内で確認を続け、より上限に近い候補へ入れ替える。
2. 方向の分散が近さより優先され、遠方候補と近場候補が混在した。近さの帯を先に比較し、方向は同程度の候補間で考慮する。経路確認順だけでなく最終8件の採用も同じ方針に統一する。
3. 外側4検索点と起点中心の間に、APIから返されにくい中間距離帯があった。車の4探索点を中間・外側へ分ける。近場への偏りも、外側だけの上限超過も抑える。

下限入力の有無を上限への近さの目標切替には使わず、上限を常に探索目標とする。推定だけで候補を棄却せず、最終採否は経路の数値で判定する。上限超過が続き8件に足りない場合は、残り経路予算を考慮して補充を優先し、8件揃ったら再び上限近くの候補への改善に使う。

## API予算

方向別の予算予約と探索履歴の最新仕様は [DIRECTIONAL_RESERVATIONS.md](DIRECTIONAL_RESERVATIONS.md) を参照。近さが同程度なら同一方位内の隣接地点も後回しにする。

方向別の実測補正については [DIRECTIONAL_CALIBRATION.md](DIRECTIONAL_CALIBRATION.md) が最新。初期の四方向それぞれの移動コストを確認してから候補探索位置を補正する。方向確認の最大4経路も24回の中に含める。前の方向の道路速度を別方向へ流用しない。四方向と最後の補正で探索目標を揃え、最後の一地域だけを上限ぎりぎりに集めることを避ける。

- Nearby最大5回、経路最大24回は維持。追加検索も通常の1検索分として予約する。
- これまで16回で終わっていた検索も24回まで確認するため、実際の利用量は増える場合があるが、全体上限の設計上の最大量は変わらない。
- 一般全体400検索/32日なら経路最大9,600回。管理者は別集計・無制限なので、この数字には含まれない。
- 有効な候補や上限近くの候補が地域全体で存在しないことを証明する全件探索ではない。Googleの返却件数・経路予算・道路事情により結果が少なくなる場合は残る。

## 自動検証

720ケースの組合せ（3移動手段×2基準×2片道/往復×3下限状態×5目的地条件×2高速設定×2初回/追加）で以下を確認する。

- 上限以内・往復合算・下限未満の補充・最大8件
- API予算、既出/除外、ID重複なし、自転車の換算、高速指定の適用
- 表示並び替えで候補ID集合が変わらない

別途、8件取得後の改善、時間/距離と高評価/レビュー数の相互作用、位置情報失敗時の検索停止、利用制限の原子的予約などを回帰検証する。合成データの検証と公開サイトの実検索確認は区別して記録する。

残課題：海に囲まれた那覇・高松では8件に満たない。仙台でも120分付近まで届いていない。この結果だけで候補が存在しないとは判断しない。固定のAPI予算内で取得する候補の地域偏りは残り、今後は陸地方向の推定や候補取得と経路確認の配分を改善する必要がある。追加検索で探索位置を変えることは可能だが、8件の追加を保証しない。

自動テストは927件合格。720組合せに加え、実測補正の内外移動、第五検索の一回限りの取得、8件確保後の改善を検証した。型検査・本番ビルドも完了。

大阪駅では距離指定も確認し、往復120kmで8件・109.7〜113.0km、下限100kmを付けても同じ8件を維持した。東京の報告座標では修正前の上位が112分に続き108分、その後39分以下だったが、中間・外側探索と経路確認継続により8件・93〜116分となった。下限90分でも8件、片道120分でも8件・100〜103分を確認した。

大阪駅・往復100〜120kmの追加検索では、元の8件の表示値を保ったまま16件へ増加した。追加分のうち下限未満2件は補充として表示された。重複ID除外の保証は自動テストでも確認する。

## 2026-11-02追補：下限空欄の遠方探索と追加表示順

- 車の時間検索は、初期探索に使う平均50km/hの距離を「到達可能性の上限」として補正検索にも適用していた。高速道路等で実測が短くても外側へ移れず、補正で取得した地点も除外される問題があった。
- 初期4検索は維持し、実測で位置を決める第五検索だけ、車・時間指定では初期距離の最大2倍（高速回避時は1.4倍、絶対値最大300km）まで補正を許容する。距離指定・徒歩・自転車の範囲は広げない。API検索円の半径50km、Nearby最大5回、経路最大24回、実測による上限判定は維持する。下限空欄／0／90で同じ補正が働く回帰テストを追加した。
- 「さらに調べる」でデータ自体は保持していたが、描画時に全件を再ソートしていたため、新候補が既存カードの間に割り込んでいた。表示順を結果の状態として保持し、新規候補だけ選択中の順序で並べて末尾へ追加する。
- 利用者が並び順を明示的に切り替えた場合のみ、その時点の全件を再ソートする。切替後の追加検索でも、その既存表示順を保持する。通常の「調べる」は新しい検索として一覧を作り直す。
- 条件順・評価順・レビュー数順の各状態で、複数回の追加後も元カードの内容と先頭順が保持されることを検証。自動テスト933件、型検査、本番ビルド合格。

公開版で仙台駅・車・高速利用可・往復120分・すべて・下限空欄を再確認したところ、最大97分（8件）であり、今回の探索距離制限緩和だけでは改善しなかった。これを解消済みとは扱わない。一方で、同じ検索から「さらに調べる」を実行すると16件となり、先頭8カードの表示テキスト全体が追加前と完全一致することをブラウザで照合した。

続けて、補正を最初の二地点だけで決めず、原則四地点の実測を比較してから実行するよう変更した。候補が四件未満なら残り候補がなくなった時点で補充する。Nearby5回・経路24回は維持。仙台駅の同条件では8件・83〜99分となった。最大値は改善したが120分付近まで十分に取得できる状態ではなく、この制限は引き続き残る。先頭二地点だけが遅い場合に残りの実測を無視しない回帰テストも追加した（合計934件）。

## 現行方式への更新
2026-11-02の追加修正で、初期4回＋補正1回から初期2回＋補正最大3回へ変更し、近さの比較帯を3%へ縮小しました。現行仕様と検証結果は [検索再検証](SEARCH_AUDIT_2026-11-02.md) を参照してください。上記の各節は当時の検証経過を含みます。
